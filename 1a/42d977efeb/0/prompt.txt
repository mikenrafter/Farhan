**1. You're right about proxies; I withdraw finding 5 as written.**
- **A source cancel leaves the proxy posted.** In `NotificationService.kt:328-341`, a source-app removal does `captureEvent(originalId, removed = true)`, then `actionStore.remove`, then `Work.Removed`. At `:84` that becomes `coordinator.onRemoved`, which calls `rows.markCleared(id)` (`NotificationDeliveryCoordinator.kt:200`). Nothing on that path calls `cancelProxy`.   - intersect it with `ids` and cancel only those (live proxies are capped at `MAX_LIVE_PROXIES = 1024`);
  - remove the retained actions for every ID in memory.

## 3. Against the one-minute re-snooze

- **It breaks I7**, because one minute later isn't a cadence tick.
- **It doesn't converge.** Every overflowed return has already made its sound (E11). Snoozing them all for one minute brings them back at one instant, so the burst repeats, possibly with a sound every minute. The 128-item intake drains slowly, because each item is classified and does I/O.
- **Raising the bound is expensive.** Each queued item can carry up to 1 024 chars of title, 16 384 chars of text and 8 actions with their intents (Svc:245-251). A return needs only its key and `postTime` once S3 (charge at the priority recorded at snooze) is accepted.

**Simpler than both:** the "pending set" is just a field on the entry you already have. `onNotificationPosted` already has to check the tracker synchronously. When it finds the key, it sets `returnedAt = postTime` on that entry and offers a small `Work.Return(key)`. Requiring one full tick also avoids a race where the next tick fires seconds after the snooze call.

## Musts

**1. The pending queries reopen a snoozed row the moment its deadline passes.** Locations: `NotificationQueriesTest.kt:52-72`; spec V3, "deadline in the future".
- **Why it happens:** Every snooze deadline is a cadence tick, and the batch tick fires at that same tick.
- **Failure:** At 10:00:00 the batch tick runs before Android's alarm has reposted the original (`Coordinator:239`). The row is not in `visibleSources` yet, so the tick sends it to `deliver()` and posts and charges a proxy. Android's return then arrives, still carrying its deadline. That gives a duplicate and a second charge, because `settleSnoozeReturn` has no rule for a row that is already delivered.
- **Why the tests can't catch it:** they only use deadline 2000 with now 1000, and the `rows()` helper ignores unused arguments. A green using `> :now` passes; so does `IS NULL`.
- **Fix:** Exclude every row whose `snoozeDeadline` is not null. Custody should end only through a settle, a fallback or the loss scan. Add three tests:
  - a deadline equal to now and one earlier than now are both still excluded;
  - `onBatchTick` with a row past its deadline posts nothing;
  - settling a row that is already delivered charges nothing.

**2. The crash order in v3.1 contradicts the red tests, and neither order is exactly-once.**
- **The contradiction:** `SnoozeReturnCoordinatorTest:50` asserts `assertThat(rig.budget.appendAttempts).isEmpty()` after a write failure. Its catches line (42) names "appending spend before the state write" as a bug. That is the existing order in `finishCompletion` (`Coordinator:115-118`: row, then budget state, then spend), and the proxy path shares that code, so reordering it touches I4. v3.1 says the opposite: spend, then budget state, then row.
- **Why neither is exactly-once:** recovery after process death re-decides the return. Suppose the process dies after the budget state is written but before the row. The rescan sees the charged budget and may deny, so it snoozes again. The next return has a new `postTime`, so a new `effectId`, and is charged a second time. `CommitPending` lives only in memory and does not survive a process death.
- **Fix:** Write the `effectId` into the budget snapshot together with the state (a small bounded set of recent ids). Order the writes state-with-id, then spend (already de-duplicated), then row. On replay, check the id before deciding anything. If that is too much for a pilot, keep row-first, accept a possible undercharge and say so in the code. Either way, add a test that rebuilds a fresh coordinator over the same stores after each step.

**3. The rescan of expired rows is the only recovery path, and it has no test.**
- **What depends on it:** both a crash before step (1) and V5 flags lost in a process death recover only through "deadline passed and key active, so settle".
- **The conflict:** that condition is the same one V6 uses to fall back (unconfirmed, active, same `postTime`). The rule that separates them, `active postTime != row.timestamp`, is not written down anywhere.
- **The gap:** Separately, the loss tests (`:399`, `:417`) both start with empty lists. Mutating the code to drop the "in neither list" check survives both.
- **Fix:** Add tests for:
  - an active key with a new `postTime` settles exactly once;
  - an active key with the same `postTime` falls back;
  - a key still in the snoozed list after its deadline is left untouched.

**4. Under shipped defaults the owner gets several beeps at midnight.** This is the one for question (4).
- **The numbers:** 22:00–24:00 has 0 points, and 00:00–09:00 has 2, which pays for exactly one HIGH. Every HIGH that arrives in the evening is planned for 00:00.
- **What happens:** The first is charged. Each of the others comes back at 00:00, beeps once (E11), is denied and is snoozed again to 09:00. The proxy path delivers one and holds the rest silently, so snooze makes nights strictly worse.
- **Fix:** When planning a snooze, also subtract the points and hourly slots already held by Farhan's live snoozes aimed at the same period. Test: two HIGH notifications at 22:30 come back at 00:00 and 09:00.

# Round 2 rebuttal: crash order, midnight cap, grouped children

Short answers:
1. **Crash order:** I agree with option (a): keep the existing order and drop v3.1's reordering. But (a) is safe only if green does two specific things, and its worst case is a little worse than you describe.
2. **Midnight cap:** a capacity cap reads the same ledger rows I meant, so there is no reservation bookkeeping either way. Your cap fixes the two-HIGH example, but it is wrong unless it is counted per period with cost weights.

## 1. Crash order: keep (a), but say exactly what it costs

**What the code does today:**
- `finishCompletion` (`Coordinator:115-118`) writes the row first, then the budget state, then appends the spend entry.
- `rows.markDelivered` is the DAO statement `UPDATE … SET isDelivered = 1 WHERE id = :id` (`NotificationDao.kt:74-75`). It does not clear `snoozeDeadline`.
- `CommitPending` is the `completion` variable, which lives only in memory and does not survive a process death.

**What a replay does after a crash between the budget-state write and the spend append:**
- The row is already `isDelivered = 1`, and its `snoozeDeadline` is still set and in the past.
- The source key is active (the original came back with a new `postTime`).
- That is exactly the rescan condition from must 3 ("deadline passed and key active, so settle").
- So if green reuses `markDelivered` unchanged, and neither the rescan nor `settleSnoozeReturn` checks `isDelivered`, the replay decides again. If the return is allowed, it charges a second time; if denied, it snoozes a notification that was already charged. **Answer: as the code stands, the rescan does not see that the row was delivered, and it double charges.**

**Two conditions make (a) safe:**
1. The row step for a return is one statement: `SET isDelivered = 1, snoozeDeadline = NULL, snoozePriority = NULL, snoozeBootCount = NULL`. That needs a new DAO query, not `markDelivered`. Once the deadline is cleared, the row drops out of `liveRows` and the rescan cannot find it.
2. `settleSnoozeReturn` refuses any row that is not live or is already delivered, and charges nothing (should S2). This is the second guard.

**Worst cases under (a) with both conditions:**

| Crash point | Outcome |
|---|---|
| Before the row step | The rescan settles it, charged exactly once. |
| After the row step, before the budget state | One return is never charged against the budget. This is the case your summary leaves out. |
| After the budget state, before the spend append | The spend log is one line short. |

There is never a double charge. The stable `effectId` only matters for the replay inside one process (and does no harm). Across a process death, a spend entry is never appended without its row already being done.

**Is (a) enough for a pilot?** Yes. It needs:
- a documented CLAIM giving the order and "may undercharge one return, never double";
- the two conditions above, pinned by tests;
- a test that rebuilds the coordinator over the same stores at each of the three crash points, asserting the outcomes in the table.

The existing proxy path has the same exposure, so nothing in shared code changes and I4 holds. **Must 2 is withdrawn.** It becomes a spec fix: strike the v3.1 reorder and keep these two conditions.

## 2. Midnight beeps: the cap works if it is counted per period

**It uses the same state.** The live ledger rows already hold `snoozeDeadline` and `snoozePriority`, so they are the reservation. "Subtract points held by live snoozes" and "count the ledger's live snoozed rows" read the same rows. The only real difference is what happens past capacity: you send it to the proxy path, I searched for the next tick. I accept yours. It is simpler, the proxy queue is silent, and it delivers at the same 09:00.

**The two-HIGH-at-22:30 example:** the 00:00–09:00 period has 2 points and a HIGH costs 2, so the capacity is one. The first notification is snoozed to 00:00. The second finds one live row due at 00:00, gets no snooze, and is queued by the proxy path for 09:00. That is equivalent.

**Where a per-tick cap breaks:** the HIGH ticks at 09:00, 10:00 and 11:00 all share the 09:00–12:00 period, which has 8 points.
- Four HIGHs at 08:30 go to 09:00, and four more at 09:30 go to 10:00.
- A per-tick cap of 8 ÷ 2 = 4 allows both groups.
- At 10:00 the period is already spent, so four returns are denied and beep four times.
- Priorities also share the points: a MEDIUM costs 4 and a HIGH costs 2.

**The rule that works:** the target period's points must be at least:
- the cost of the live rows whose deadline falls in that period (cost-weighted by `snoozePriority`);
- plus the spend already recorded in that period (the v3.1 rule);
- plus this notification's cost.

**The hourly cap:** `MAX_HOURLY_PASSTHROUGH = 10` is counted per `passthroughWindowKey`, not per tick (`NotificationDeliveryPolicy:26,145`). In testing mode several ticks share one window. Count the live rows due in the same window, plus `hourlyCount` if that window is the current one.

This is one pass over `liveRows()`, which is at most 400 rows, with no new columns.

**A race the cap does not fix:** at the 00:00 tick, `onBatchTick` can spend those 2 points on a queued proxy row before the native return settles. The return is then denied and beeps. Proxy selection should also leave out the points of live snoozes due at the current tick. This is a should.

**Does the Do Not Disturb mute change the severity?** It would, if it ships the way round 2 recommends. Under Farhan's Priority mode the probe silenced a source message entirely ("intercepted with no beep or buzz", `notification-sound-control.md` round 2). Denied returns would then only flash in the shade. But it is not built yet, it needs a Do Not Disturb access grant, and the owner can turn it off. Also, round 2 notes that a global open window "cannot enforce a per-item budget". If elected items are announced through that window rather than the bypass channel, a charged return at 00:00 opens it exactly when the denied ones arrive. **My recommendation:** ship the cap now; it costs one loop. Downgrade must 4 to a should once the mute ships with the bypass-channel design.

## 3. Grouped children: snooze them, but stop Farhan cancelling summaries

**What the code shows:** the proxy path has no handling for summaries at all. Nothing in the data or domain modules checks `FLAG_GROUP_SUMMARY`. A summary is classified, stored as a row, and listener-cancelled like any other notification (`NotificationService.kt:310`).

**The cascade (from my memory of AOSP; (f) must confirm it):** a listener cancel of an app summary runs `cancelGroupChildrenLocked`. That cancels the group's active children with `REASON_GROUP_SUMMARY_CANCELED` (12). It walks the active and enqueued lists, not `SnoozeHelper`.

**The loss paths with snooze on and children allowed:**
1. **The usual messaging-app pattern.** The app posts the child and the summary together. Farhan's worker snoozes the child, but the summary reaches the proxy path while the child is still active. Farhan cancels the summary, and the cascade cancels the child with reason 12. The ledger row has a deadline. At the deadline the key is in neither list on the same boot, so the row is marked cleared. **That is a silent loss.**
2. **An only child.** Snoozing an only child also snoozes its summary (flexibility doc §1). Both come back at the deadline. The child is charged and left visible. The summary is not Farhan's, so it is skipped as `GROUP_SUMMARY` and goes to the proxy path. Farhan cancels it, and the cascade cancels the charged child. Its row is already delivered, so no proxy follows. **That is a loss after charging.**
3. **A summary that comes back alone.** A summary snoozed alongside our child returns. If we leave it alone it is harmless noise, so on its own it needs no handling. It only matters through path 2.
4. **The source cancels the summary.** That is the source's own intent, the same as a source cancel. Clearing is correct.

Paths 1 and 2 are caused by Farhan's own intercept, so the ledger can make them safe:
- **(a) Leave summaries alone while snooze is on.** Do not cancel a summary and do not store a row for it: summaries carry no message of their own in current apps. This removes the cascade at its source.
- **(b) Treat reason 12 on an owned key as collateral, not cancellation.** That means a snoozed or returned child. Put the saved row back as pending. If it was already charged, send it through the existing refresh path, which posts a proxy without charging again.
- **(c) Restore missing grouped rows on the same boot.** Rule: same boot, key missing, row has a group key, so restore it as pending instead of clearing it. This trades a rare stale proxy for a cancelled message against a silent loss, which matches your first priority.

**A related test error.** The research says a source cancel of a snoozed record has no removal callback; the record just lingers in the snoozed list until its deadline (flexibility doc line 73). But `SnoozeHandlerTest:279-292` drives `onRemoved(…, REASON_APP_CANCEL)` for a snoozed key. That test contradicts the research and should go through the scan path instead (should). A green that relies on that callback would never see the cancel on a real device.

**Pass and fail criteria for device evidence (f).** Run on the API 35 emulator on Boat, with a fixture publisher using `setGroup` plus an app summary, in two variants: `GROUP_ALERT_CHILDREN` and `GROUP_ALERT_SUMMARY`. Use the green build with snooze on.

| F1 | Two children and a summary, posted together | Both children receive `REASON_SNOOZED` and appear in the snoozed list. At the deadline both come back with the same keys and new `postTime`s, and each is settled once in the ledger. Record whether the summary is visible while the children are hidden (shade screenshot). |
| F2 | An only child and a summary | Record whether Android snoozes the summary too. After the return, the child is still active 60 s later and gets no reason-12 removal. Its row is delivered and charged once. |
| F3 | A new child plus a summary update while a child is snoozed (the messaging-app pattern) | The snoozed child stays in the snoozed list and comes back at its deadline. The new child is snoozed or proxied. No owned key gets a reason-12 removal. |

   - **CRITICAL is unaffected:** CRITICAL, exception and system-exempt items are pass-through (`NotificationService.kt:321`). `onArrival` returns before posting them, line 327 never cancels them, and they are never elected.
   - **Batch items are not retried forever:** the failed post triggers a reconcile. That leaves the state `Suspended` even if removal fails, and `electionFor` returns nothing unless the state is `Held`. So the next tick posts on the normal channel.
   - **The queue stalls for one period, not forever:** a failed head holds its app and priority group until the next tick, which is an hour for HIGH by default. With the fallback in place, that tick delivers instead.

   - **Nothing recreates the rule:** with the rule gone and the saved state still On, the reconciler reports "stopped in Settings" and takes no action. Only `enable()` can create or turn on a rule.
